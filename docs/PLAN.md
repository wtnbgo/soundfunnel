# SoundFunnel 計画書

複数 PC のサウンドを LAN 内の 1 台（「サーバ」）に集約して再生する常駐アプリ。
SonoBus をコードベースとし、セッション・録音・エフェクト等を省いた単機能版にする。

## 1. ライセンス確認

| 部品 | ライセンス | 扱い |
|---|---|---|
| SonoBus 本体 (`sonosaurus/sonobus`) | GPLv3 + 第7条例外（アプリストア配布許可） | 流用可。派生物は GPLv3 で公開。著作権表記を残す |
| AOO (Audio over OSC, SonoBus 同梱版) | BSD (Standard Improved BSD) | 流用可。LICENSE 同梱 |
| ff_meters | BSD 3-Clause | 使う場合は LICENSE 同梱 |
| JUCE 7.x | GPLv3 / 商用の選択制 | GPLv3 を選択。スプラッシュ表示不要 |
| Opus | BSD 3-Clause | ソースからビルド |
| ASIO SDK | Steinberg 独自 / GPLv3 選択可 | 初期版は使わない（WASAPI/CoreAudio/ALSA で足りる） |

結論: **本アプリを GPLv3 で公開すれば流用に問題なし。** 注意点は次の 2 つ。

- `SonoBus` の名称・ロゴは使わない（商標配慮）。README に「SonoBus 由来」と明記する。
- JUCE 8 は AGPLv3 なので、GPLv3 で揃えるため JUCE 7 系（7.0.12）に固定する。

## 2. SonoBus からの変更点

| SonoBus | SoundFunnel |
|---|---|
| 全員が全員に送る（フルメッシュ）、各自で個別ミュート | **クライアント → サーバの一方向**のみ。サーバだけが再生 |
| 接続サーバ (aoo.sonobus.net) 経由のグループ参加 | **LAN 内自動検出**。共有キーが一致する者同士でグループ |
| 録音 / サウンドボード / メトロノーム / エフェクト / チャット / VST プラグイン | **全削除** |
| 通常のウィンドウアプリ | **常駐（トレイ）アプリ**。設定画面はトレイから開く |
| — | **サーバは移動可能**。最後に「サーバになる」を押した PC がサーバ |

流用するもの: AOO の送受信（ジッタバッファ・Opus/PCM コーデック）、コーデック形式の選択肢、
デバイス設定まわりの考え方。SonobusPluginProcessor は 9,700 行で機能が密結合しているため、
丸ごと削るよりも **AOO 周りの処理を参考にした小さなエンジンを新規に書く** 方針にする。

## 3. 構成

```
┌ 各 PC (同じバイナリ) ─────────────────────────────┐
│ TrayApp ─ SettingsWindow (デバイス/形式/キー/ミュート) │
│    │                                                   │
│ Discovery (UDP マルチキャスト, HMAC 認証)              │
│    │ 仲間一覧・サーバ宣言                              │
│ Election (最後に宣言した者がサーバ)                    │
│    │ role = server / client                            │
│ AudioEngine (AOO)                                       │
│   client: 入力デバイス → aoo source → サーバへ送信     │
│   server: aoo sink × N → クライアント別ミュート → 出力 │
└────────────────────────────────────────────────────────┘
```

### 3.1 LAN 内の自動検出（技術選定）

候補:

1. **mDNS / DNS-SD (Bonjour)** — 標準的だが Windows は Bonjour か Win10 以降の DnsService API、
   Linux は Avahi が必要で、3 OS で実装が分かれる。キーによる絞り込みは結局自前。
2. **UDP マルチキャストのビーコン（自前）** — 依存なし。JUCE の `DatagramSocket` で 3 OS 共通。
3. 接続サーバ（SonoBus 方式） — 外部サーバが必要で、要件（LAN 内自動）に合わない。

→ **2 を採用。** 仕様:

- 宛先: マルチキャスト `239.255.77.77:47700`（組織内スコープ）。マルチキャストが通らない環境向けに
  同ポートのブロードキャスト `255.255.255.255` にも送る。
- 1 秒ごとにビーコン送信。5 秒届かなければ離脱扱い。
- パケット = ヘッダ + 本文(JSON) + `HMAC-SHA256(groupKey, ヘッダ+本文)`。
  - ヘッダに `groupId = SHA256("soundfunnel-group:" + groupKey)` の先頭 8 バイトを入れ、他グループは即破棄。
  - HMAC が合わないものは破棄（キーを知らない者はなりすませない）。
  - 本文に送信時刻と連番を入れ、古いものの再送（リプレイ）を弾く。
- 本文: `nodeId`(UUID), `name`, `audioPort`, `serverClaim{epoch, nodeId}`, `version`。

### 3.2 サーバ選出（「最後に名乗った者」）

- 各ノードは知っている最新の宣言 `claim = (epoch, nodeId)` を保持し、ビーコンに載せ続ける。
- 「サーバになる」を押すと `epoch = 知っている最大 epoch + 1` で宣言し直す。
- 受信した宣言のうち `(epoch, nodeId)` が辞書順で最大のものを採用 → 全員が同じ結論に収束。
- 宣言されたサーバが 5 秒消えた場合: サーバ不在（音は止まる）。自動で別 PC に移すことはしない
  （要件は「最後に選んだところ」なので）。サーバ PC が再起動して戻れば自動で再開する。
- 宣言は設定ファイルに保存し、再起動後もグループの状態を引き継ぐ。

### 3.3 音声転送

- 各ノードは UDP ポート 1 つ（既定 47701、使用中なら空きポート）を AOO 用に開き、ビーコンで通知。
- クライアント: `aoo::isource` を 1 つ作り、サーバのエンドポイントを sink として追加。
  サーバが変わったら sink を差し替えるだけ。
- サーバ: クライアントごとに `aoo::isink` を作り（ID = 検出時に割り当て）、受信音を合算して出力。
  クライアント別に **ミュート / 音量** を持つ（ミュートは送信側にも通知して帯域を止める）。
- 自分がサーバのときは、自分の入力を出力に混ぜるかどうかを設定で選べる（既定オフ）。
- 形式: SonoBus と同じ選択肢（Opus 16–256 kbps / PCM 16・24・32bit）、チャンネル数 1–2。
- ジッタバッファは SonoBus の初期値（自動調整）に倣う。

### 3.4 「PC の再生音」を拾う方法（重要な注意点）

要件の目的（PC で鳴っている音を集める）には **ループバック録音** が要るが、JUCE 標準の
デバイス層は入力デバイスしか扱えない。OS ごとの対応:

| OS | 方法 | 予定 |
|---|---|---|
| Windows | WASAPI ループバック（出力デバイスを録音） | **独自 AudioIODeviceType を追加（M4）**。それまでは VB-CABLE 等の仮想デバイスで代用可 |
| macOS | 14.2+ の Core Audio Process Tap / それ以前は BlackHole 等の仮想デバイス | M5 で Process Tap を検討。当面は仮想デバイス |
| Linux | PulseAudio / PipeWire の monitor ソース | JUCE の ALSA 経由で `pulse` を選び、monitor を既定入力に設定すれば可。M5 で案内を整備 |

### 3.5 常駐動作

- JUCE の `SystemTrayIconComponent`（Win/Mac。Linux は環境依存のためウィンドウ最小化でも可）。
- トレイメニュー: 状態表示（サーバ名・自分の役割）/ サーバになる / 送信の一時停止 / 設定 / 終了。
- 自動起動: Windows = レジストリ Run キー、macOS = LaunchAgent、Linux = `~/.config/autostart`。
  インストーラ（M6）で登録し、設定画面でオン/オフ可能。
- 設定保存先: `juce::PropertiesFile`（OS 標準のアプリデータ位置）。

### 進捗（2026-11-12）

- M1・M2・M3 の実装済み。Windows でビルドできることを確認した（Debug）。
- 1 台で 3 インスタンスを起動して確認した内容: 自動検出、別キーのノードが見えないこと、
  サーバの移動、ミュート（送信側も停止する）、サーバの再起動からの自動復帰、テストトーンがサーバに届くこと。
- 未確認: 実スピーカーで聴いて確かめる音質と遅延。
- 同じ PC で試すときは `--silent --test-tone` を付ける（マイクとスピーカーのハウリングを防ぐ）。
- 3 OS でビルドとセルフテストが通った（Windows 11 / Ubuntu 26.04 / macOS 15.8 Intel + Xcode 26.3）。
- Windows ↔ Linux の LAN 実機テストで、検出・接続・サーバの移動・テスト音の受信を両方向で確認した。
- Windows・Linux・macOS の 3 台を LAN でつないだ実機テストで、次を確認した:
  - 3 台とも互いを検出し、クライアント 2 台のテスト音がサーバに届く（Linux 44.1 kHz と、Mac・Windows 48 kHz の混在でも届く）。
  - サーバからのミュートでクライアントの送信が止まり、解除で再開する（3 OS とも）。
  - サーバを Windows → Linux → Windows と移しても、残る 2 台の音がそのつど新しいサーバに届く。
- macOS の受信が止まっていた原因は、ファイアウォールではなく「ローカルネットワーク」の許可だった。
  許可されるまではマルチキャスト送信が EHOSTUNREACH で失敗し、何も受信できない。
  Info.plist に NSLocalNetworkUsageDescription を入れ、許可ダイアログで許可すると届くようになった。
- macOS で入力付きのデバイス（BlackHole など）を開くと、入力を使わなくてもマイク許可の確認が走り、
  答えが出るまで CoreAudio がブロックしてアプリ全体が固まっていた。
  AVFoundation でマイク許可を先に確認・要求し、答えが出てからデバイスを開くようにした。

### 既知の課題・TODO

- Linux のトレイ: JUCE の Linux 版トレイ (XEmbed) を GNOME (Wayland/Xwayland) に埋め込むと、
  gnome-shell が BadWindow で abort した。いまは Linux ではトレイを作らず、通常のウィンドウで動かしている。
  StatusNotifierItem (D-Bus / AppIndicator) での実装を M5 で検討する。
- macOS: ad-hoc 署名だとビルドのたびに別アプリ扱いになり、マイクとローカルネットワークの許可を
  毎回取り直す。固定の Developer ID で署名・公証する (M6)。初回起動時の許可の案内も UI に出したい。
- サーバでの受信レベルが、Mac から（0.14）と Windows・Linux から（0.10）で少し違った。
  サンプルレート変換かピークの測り方によるものとみられる。実害はないが、あとで確認する。
- 音声デバイスを 1 つも開いていないとオーディオのコールバックが動かず、サーバが受信音を処理できない。
  出力デバイスがないサーバ向けに、タイマーで処理を進める仕組みを検討する。
